### Concurrency Control Engines: Two-Phase Locking vs. MVCC
To enforce transaction isolation boundaries under ACID design principles, database engines rely on two fundamental concurrency paradigms:
* **Pessimistic Concurrency Control (2PL / Two-Phase Locking):** Transactions acquire explicit read (shared) or write (exclusive) locks on data blocks before executing mutations. 2PL ensures absolute serializability but degrades performance under high-concurrency write contention because readers block writers, and writers block readers.
* **Optimistic Concurrency Control via MVCC (Multi-Version Concurrency Control):** Instead of locking rows synchronously, the engine preserves historical, point-in-time snapshot mutations of data records using hidden system columns (e.g., `xmin` / `xmax` transaction IDs in PostgreSQL). Readers do not block writers, and writers do not block readers, allowing maximum system concurrency.

### Critical Failure Modes & Concurrency Anomalies

#### 1. Phantom Reads Under Repeatable Read (RR) Isolation
While standard ANSI SQL specs imply that the `Repeatable Read` isolation tier eliminates non-repeatable anomalies, structural variations across implementations create unexpected behaviors.
* **The Vulnerability:** Under a standard MVCC database like PostgreSQL, `Repeatable Read` natively mitigates phantom reads by evaluating a fixed snapshot at the beginning of the transaction. However, in alternative engines like MySQL InnoDB, a transaction running in `Repeatable Read` utilizing a mix of *Consistent Non-locking Reads* (`SELECT`) and *Locking Reads* (`SELECT ... FOR UPDATE` or `INSERT`) will experience phantom anomalies.
* **The Failure Scenario:** Transaction 1 reads a range of accounts via standard `SELECT`. Transaction 2 inserts a brand-new account row matching that range and commits. If Transaction 1 subsequently issues a write mutation or a locking read over that same range, the engine forces a look past the local snapshot to the active table heap, surfacing the "phantom" row inserted by Transaction 2.
* **Mitigation:** Elevate isolation explicitly to `Serializable` or enforce explicit range locks (Next-Key Locks / Gap Locks) at the application layer using `SELECT ... FOR UPDATE` during the initial query phase.

#### 2. Lock Escalation Deadlocks Under High-Velocity Contentions
When a relational database engine (e.g., Microsoft SQL Server) encounters high-volume, concurrent updates across granular blocks, its lock manager dynamically adjusts allocations to optimize memory footprints.
* **The Failure Loop:**
    1. Transaction 1 and Transaction 2 both acquire thousands of shared row locks (`S`) across different records within the same physical disk page table.
    2. As memory thresholds saturate, the database engine executes **Lock Escalation**, attempting to convert individual row locks into a single exclusive table-level lock (`X`).
    3. Transaction 1 waits for Transaction 2 to release its row locks so it can acquire the exclusive table lock. Simultaneously, Transaction 2 blocks waiting for Transaction 1 to yield its rows.
    4. This circular lock dependency creates an immediate database-tier deadlock, forcing the kernel engine to kill one of the transactions arbitrarily.

#### 3. Long-Running Transactions & MVCC Snapshot Bloat
Because MVCC relies on maintaining multiple concurrent row versions for readers, deleting or updating records does not immediately overwrite data blocks on disk. Old row versions are tombstoned as "dead tuples."
* **The Failure Mode:** If an analytical worker or developer opens a long-running transaction or holds an uncommitted read session open for hours, the database engine must retain *all* dead tuples generated by alternate concurrent write transactions across the entire system to preserve that session's point-in-time snapshot view.
* **The Operational Impact:** Background vacuuming or purging processes (e.g., PostgreSQL autovacuum) stall, preventing the cleanup of dead tuples. The physical table space on disk bloats, primary indices lose cache locality, and sequential page scanning latencies explode, degrading global application performance.
* **Mitigation:** Implement strict maximum runtime execution timeouts (`statement_timeout`, `idle_in_transaction_session_timeout`) on all backend application connection pools.
